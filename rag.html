System Architecture — Two Phases, Shared Stores

Ingestion writes vectors to LanceDB and metadata to SQL Server; query-time reads from both.

One call, many doors. Every ingestion source converges on process_document(), which embeds chunks into LanceDB and upserts metadata into SQL Server. At query time RAGPipeline.run() reads both stores, assembles a cited context block, and hands it to the LLM with a strict "answer only from context" instruction.

03

Vector Storage — Backends & the Single-Writer Thread

LanceDB is the default required backend; Azure AI Search takes over if its env vars are set.

Why a single writer? LanceDB is not safe for concurrent writers across threads/processes, so every mutation is queued as a _WriteJob to one background thread and the caller blocks until it completes. All three backends (LanceDB, Azure, legacy SQL) expose an identical method surface, so switching backends needs no changes outside vector_store.py.

04

Retrieval Pipeline — RAGPipeline.run()

Access filter → cache → hybrid retrieve + rerank → confidence → guard → cited context.

BM25 runs only on the 20 ANN candidates, not the whole corpus — keeping the keyword pass cheap. Reranking and BM25 both degrade gracefully: a missing library logs once and is skipped for the rest of the process. A tracing or cache failure never fails the request (bare try/except).

Access Control & Connector Watchers

Who can see a document, and how filesystem / SharePoint folders auto-ingest into the same pipeline.

Both watchers feed search_connector_knowledge, which scopes retrieval to app_documents rows matching a given source_watch_id + source_watch_type. Archived files are never re-ingested, and re-scanning an unchanged system/connector file (uploader id 0) refreshes it in place rather than duplicating.
